# iOS optional-account release — October 9, 2026

## Scope and current evidence

The build-41 candidate enables production Clerk accounts on iOS through the
`native_accounts` capability. `free_offline_mvp` remains the purchase guard:
no native real-money purchases are enabled. Android and iOS build 40 remain
within their existing offline account scope.

This document records preparation. It does not record a deployed backend,
published replacement policy, successful native production login, store upload,
or approval. Current runtime/API evidence must be attached after source freeze.

- Existing App Store Connect app: `6818416048`, bundle
  `com.blubberandbyte.waddlewars`. The October 9 runbook records build
  `1.0.0 (40)` delivered and assigned to `Waddle Wars Internal`, with automatic
  future-build distribution disabled. Version 1.0 with build 40 was submitted as
  `37f88032-6ebf-46a0-8909-4428710124a8`, **Waiting for Review** at that observation.
- October 8 App Privacy receipt records published Email Address, Customer
  Support, Coarse Location, and Product Interaction, each App Functionality,
  linked to identity, no tracking. That receipt covers the prior scope; it does
  not accept the account-enabled candidate.
- Production Clerk Google scope receipt records `openid`, `userinfo.email`,
  `userinfo.profile`, including name/profile picture and email consent. Native
  auth agent observed email code sign-in enabled October 9. Current Google and
  other provider configuration still needs a retained readback for this release.
- Account data flow: explicit sign-in starts Clerk; the native token and PKCE
  verifier stay in memory. Production identity is namespaced `clerk_live:` on
  the game backend. Signed-in completed runs may submit scores; Post Local Best
  is explicit. Public alias defaults to Penguin and is independent of the
  private social-login name. Authenticated sync includes earned progression,
  cosmetics, achievements, missions, best results and gameplay statistics;
  settings and time-trial ghost files stay local.
- Deletion removes active game profile/scores/save/native-session records and
  requests Clerk identity removal. It preserves earned local progress and
  minimal retirement/status/recovery-receipt records. Provider identity cleanup
  and retained-record review are distinct statuses. No complete-erasure claim
  is supported by the current protocol.

## Before internal TestFlight upload/distribution

1. Freeze sources, complete applicable local game/release checks, export iOS
   with `native_accounts`, and run the existing strict signed archive/IPA
   verifiers. The separate Android candidate is unnecessary for this iOS-only
   account release. Old `release_audit.py` deliberately rejects accounts.
   When a provisioning profile is renewed, install the **same pinned file** in
   `~/Library/Developer/Xcode/UserData/Provisioning Profiles/<profile-uuid>.mobileprovision`
   before archiving. Check its SHA-256 against the private source copy. Xcode
   cannot resolve `PROVISIONING_PROFILE_SPECIFIER=<profile-uuid>` from a copy
   kept only in the release evidence directory, even when the profile's CMS
   and certificate checks pass. Keep each failed archive run; retry in a fresh
   0700 run directory after installing the profile.
2. Retain read-only production deployment/schema/binding observations and the
   native production sign-in/cancel UI observation using the authorized existing
   session. Validate score/alias behavior, save revision/concurrency handling,
   deletion/write fences, and recovery against the **exact frozen Worker,
   modules and schema in isolated real D1**, paired with native-client
   integration. Refresh/sign-out/error paths may use that isolated integration;
   label each environment explicitly. Simulate identity-provider deletion
   responses and record that limitation. Do not create synthetic production
   accounts, scores or saves, and do not delete a production account as a release
   test. Permanent deletion of a real account requires explicit user action and
   confirmation. Isolated evidence does not prove live production deletion or
   provider cleanup. Simulator evidence does not claim the App Store IPA ran on
   a physical phone.
3. Publish the three reviewed `web/native/` HTML sources and retain actual HTTPS
   response bodies/URLs/status/date. `native_account_policy_delta.json` pins the
   prepared bytes and the previous publication hashes; it is explicitly not a
   new publication receipt. Prior `native_privacy_inventory.json` records stay
   historical. Pin the untouched public response as `body`, never an R2 object
   or normalized copy. The gate accepts exact source bytes or those same bytes
   with the single, pinned October 9 Cloudflare Web Analytics script immediately
   before `</body>`. Its output records both hashes and the comparison method;
   different scripts, tokens, placement, whitespace or policy content fail.
4. Copy `ios_account_acceptance.template.json` to a fresh evidence directory.
   Populate exact source/version/build/IPA identity, native environment and
   observed date. Set a check to `passed` only after its stated observation;
   attach non-secret evidence files with absolute paths and SHA-256. Set
   `state` to `ios_account_acceptance_recorded` only when all checks are complete.
5. Run the account gate immediately before upload:

```sh
python3 tools/release/ios_account_release_audit.py \
  --ios /absolute/frozen/candidate \
  --ios-run /absolute/verified/archive-run \
  --acceptance /absolute/evidence/account-acceptance.json
```

The gate verifies receipt/file continuity and fails on stale source, different
IPA, missing native evidence or unmatched published policies. A pass means
`ready_for_internal_testflight_upload`, never `store_ready`. It cannot infer the
truth of an observation from a test log or fabricate acceptance. Its behavior
checks use isolated real D1 plus native-client integration; the required live
scope is native authentication UI and read-only deployment/configuration
observations. Missing or failed checks stay pending in their stated environment.
No live destructive account test is required or authorized by this gate.

After upload, verify processing and export compliance for the exact new build.
Save account-specific **What to Test** and **Test Information**, then explicitly
assign that build to **Waddle Wars Internal**. Validate the TestFlight-installed
app on iPhone. These build-specific portal steps occur after processing, not as
proof before upload. External testers may require Beta App Review. Apple's
[TestFlight workflow](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/)
describes these separate steps.

Suggested What to Test: branded cold launch; iPhone camera/home-indicator
clearance in portrait and landscape; swipe penguin/equipment selection; native
production sign-in and cancellation; avalanche visibility after losing a life.
Run score, save and deletion scenarios against the isolated backend/native-client
fixtures. Do not seed synthetic production accounts or scores. On the delivered
app, inspect the deletion entry point without confirming a real account deletion;
permanent deletion remains a deliberate user action with explicit confirmation.

Apple requires accurate first- and third-party collection declarations, including
optional account data; see [App Privacy details](https://developer.apple.com/app-store/app-privacy-details/).
Its [login guideline 4.8](https://developer.apple.com/app-store/review/guidelines/#sign-in-with-apple)
sets the equivalent-login conditions. Its [account deletion guidance](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion)
requires an accessible in-app deletion initiation path and clear treatment of
retained information. These are App Review readiness items, not a claim that
Apple requires updated App Store screenshots before an internal upload.

Android's existing build-40 review and Data Safety are unaffected by enabling
accounts exclusively in iOS 41. A future Android account capability requires its
own binary, runtime and disclosure review.
